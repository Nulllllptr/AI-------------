# 設計ガード

開発者はこの手順を意識していないものとして扱い、Claudeの側から補う。

## 1. 介入の型

実装せず、次の形で3行以内に返す。長い前置きは書かない。

```
この依頼だと差分が[概算]行になります。先に3点だけ確定させます。
1. 何をするか: [Claudeの推定]  2. どこに置くか: [Claudeの推定]  3. なぜこの案か: [Claudeの推定]
この推定で進めてよいか、違う場合はどこが違うかだけ教えてください。
```

推定を空欄にして開発者に質問を返さない。必ずClaudeが埋めた案を提示し、可否だけを問う。
開発者が「それでいい」と答えられる形にすることで、設計の言語化コストを開発者に戻さない。

## 2. 介入後に必ず行うこと

### 2-1. 分割案の提示
「入力・処理・出力」の単位に分解し、1単位ずつ実装できる順序で列挙する。
1単位あたりの想定差分が200行を超えるものは、さらに分割する。
各単位には、テストで確認できる形の受け入れ条件を1つ付ける。

### 2-2. 対象外の明示
今回やらないことを明示する。開発者が言及していなくても、Claudeの側から線を引く。

### 2-3. 既存方針の要約
既存コードに触れる場合、対象ファイルを読み、
既存の命名規則・層の責務分担・エラー処理方式を3行以内で要約してから設計案を出す。
要約と矛盾する実装が必要な場合は、実装せずに理由を先に述べる。

### 2-4. 代替案の併記
設計案には代替案を1つ以上添え、却下する理由を書く。
開発者が案を1つしか見ていない状態にしない。

### 2-5. フロー図(HTML)の作成
2-1で分解した「入力・処理・出力」の単位を、矢印でつないだフロー図としてHTML形式のファイルに必ず起こす。箇条書きの文章だけで済ませない。

- 各単位(入力/処理/出力)をノードにし、処理の流れを矢印でつなぐ。分岐・並行処理がある場合はそれも表現する。
- 保存先はスクラッチパッドを既定とする。プロジェクト側に設計ドキュメントの置き場所が指定されている場合はそちらに従う。
- 3番(最終確認)より前、実装より前に提示し、開発者がフロー全体を見た上で可否を判断できるようにする。
- 見た目の作り込みは不要。ノードと矢印の対応関係が読み取れれば足りる。図示にArtifactツールでの公開が必要な場合(開発者が見やすさを優先する場合)は別途確認してから公開する。

## 3. 設計を確定させる前の最終確認

確定前に、Claudeの側から次の3観点で穴を出す。開発者からの依頼を待たない。

- 想定の10倍の負荷がかかったとき、最初に壊れるのはどこか
- 悪意ある入力が来たとき、どこから入るか
- 6ヶ月後に別の人が変更するとき、どこが読み解けないか

該当がない場合は「この3観点では問題を検出せず」と1行で述べる。省略しない。

## 4. 繰り返さない条件

- 開発者が「設計は決まっているので実装して」と明示したら、1〜3は行わず実装に進む。
  ただし差分200行の上限と、対象外の明示は維持する。
- 同じセッションで既に介入した内容は、2回目までとする。
