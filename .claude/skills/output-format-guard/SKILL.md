# 出力フォーマットガード

内容の型に応じてパターンを選ぶ。存在しない型に無理に当てはめず、複数パターンを組み合わせるか、見出しと箇条書きだけで組み立てる。
全出力に共通する原則(結論を先に、指摘には提案を添える等)は個人用CLAUDE.mdの「出力の構造化」を参照。ここにあるのは型ごとの具体的な骨組み。

## 1. パターンの選び方

| 内容の性質 | 使う型 |
|---|---|
| 問題点・改善点を洗い出す | 2. 指摘パターン |
| 実装方針・変更内容を提示する | 3. 実装提案パターン |
| 複数案から1つを選ぶ | 4. 比較パターン |
| 作業結果・完了状況を伝える | 5. 完了報告パターン |
| 調査・確認の過程を示す | 6. 調査ログパターン |
| 外部の記事・公式ドキュメントを根拠に回答する | 7. 参照情報パターン |

複数の性質が混ざる場合はパターンを連結してよい(例: 指摘パターンで洗い出してから比較パターンで対応順を決める)。

## 2. 指摘パターン

1件の指摘は次の3要素を1セットにする。1つでも欠けたまま出力しない。

- **現状**: どこに何があるか(ファイル名:行番号)
- **問題**: それがなぜ問題か
- **提案**: どう直すか、または選択肢

複数件は重大度(高→低)の順で並べる。件数が3件を超える場合は表(現状/問題/提案の列)にする。
「提案」が思いつかない指摘は、指摘自体を保留するか「提案は要検討」と明記する。書かずに省略しない。

## 3. 実装提案パターン

実装を提示する直前に組み立てる。

1. 結論: 「(機能)は現在〜だが、この実装で〜になる」という before/after 形式・1行。ファイル名やコード用語ではなく機能・挙動で書く
2. 理由: なぜこの実装か(1〜2行)
3. 却下した代替案: 表(案 / 却下理由)。1件もない場合のみ省略可
4. 実装(コード差分): 1の機能変更を実現する手段として提示。「これを実現するためにこのようなコードを実装します」という位置づけ。差分は要約・省略せずそのまま示す
5. 依頼範囲外の変更: 箇条書き。なければ「依頼範囲外の変更なし」
6. テスト整合の申告: 該当する場合のみ書く。該当なしなら省略してよい

## 4. 比較パターン

1. 推奨: 結論を先に1行で示す
2. 比較表: 列に観点、行に選択肢を置き、トレードオフを一目で見せる
3. 推奨理由: 1〜2行。表を読み返させない

## 5. 完了報告パターン

1. 変更したこと(機能ベース): 「(機能)は〜だったが、〜になった」という before/after 形式の箇条書き。ファイル名だけの列挙にしない
2. 実現方法(コードの補足): 1の各項目に対応させ、「これを実現するためにこのようなコードを実装/削除した」という位置づけでコード差分を示す。ファイル名:行番号込みで、要約・省略せずそのまま示す
3. 依頼範囲外の変更: なければ「依頼範囲外の変更なし」
4. 未確認・残作業: あれば列挙、なければ「なし」

## 6. 調査ログパターン

Grep/Read/Bash等で調べてから結論・報告を出す場面で使う。5. 完了報告パターンや2. 指摘パターンの根拠として組み込んでもよい。

表の前に、調査の流れを観点だけ→でつないだ1行で示す。次に表で各ステップの詳細を示す。表は指摘パターンと違い重大度順ではなく、必ず調査した時系列順に並べる。

**流れ**: ①〈観点〉→ ②〈観点〉→ ③〈観点〉

| 順 | 観点 | 確認コマンド | 判断 | 対応 |
|---|---|---|---|---|
| 1 | (20字程度) | 実際に使ったコマンド(要約しない) | (20字程度) | 実装・編集した内容。なければ「実装・編集なし」 |

- 「順」は調査を行った順番の通し番号。前のステップの結果が次のステップのきっかけになった場合(例: 検索結果を受けて特定ページを直接確認した)は、その前のステップの「判断」に「→次で確認」のように次への橋渡しを一言添える。
- 流れの1行は観点だけを並べる。判断・理由はここに書かず表に譲る。
- 観点・判断は20字程度に圧縮する。詳細はここに書かない。
- 確認コマンドは実行したものをそのまま書く。
- 実装・編集を伴わない調査のみの場合、対応列は「実装・編集なし」と明記する。省略しない。
- 結論に寄与しなかった探索(ヒットしなかった検索、途中で切り替えた方針など)は載せない。全件載せるとアウトプットが肥大化する。
- 調査が1件のみなら流れの1行と表は省略し、①〜④を箇条書き4行で済ませてよい。

## 7. 参照情報パターン

外部の記事・公式ドキュメントを検索して回答の根拠にしたときに使う。個人用CLAUDE.mdの「外部ライブラリ・API・仕様など裏付けが必要な調査は…」の運用形。

引用の示し方は2通り。文脈に応じてどちらかを使う(併用可)。

- **本文中で明示する形**: 該当箇所の説明に続けて「(〇〇の公式ドキュメントのこの記述からこう判断した)」のように、参照箇所と読み取った内容をセットで書く。個別の主張ごとに根拠を示したいときに使う。
- **末尾に一覧化する形**: 回答の最後に情報源をまとめる。項目が複数あるときに使う。

  - `[タイトルまたはページ名](URL) — 何を確認するために参照したか`

- 記憶(学習知識)のみに基づく部分と外部情報で裏付けた部分が混在する場合は、記憶由来の箇所を「(未確認・知識ベース)」等で区別する。断定できない場合は個人用CLAUDE.mdの「断定できない仕様・挙動は推測で書かない」に従う。
- 検索しても該当情報が見つからなかった場合は、その旨を明記し、それでも記憶で答えるなら「(未確認)」と明示する。

## 8. 崩してよい場面

- 1〜2行で済む直接回答には適用しない。
- 該当パターンがない内容を無理にどれかへ当てはめない。見出し+箇条書きの基本構造だけ守れば良い。
- 同じ内容を毎回同じ見出し文言で繰り返さない。型は骨組みであって、文言まで固定するものではない。
