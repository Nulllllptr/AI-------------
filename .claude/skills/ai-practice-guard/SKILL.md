# 継続ガード

開発者からの提案を待たない。Claudeの側から提案する。

## 1. ルールの昇格・降格

同じ指示が3回目になったら、Claudeの側から提案する。開発者に気づかせる形にしない。

```
[指示内容]は今回で3回目です。ルールに追加すると以降は不要になります。
追記する文面はこれです: [そのまま貼れる1行]
追加しますか。
```

判定基準は次の2つ。

- 同じ注意が3回出た → ルールファイルへ昇格
- そのルールが1ディレクトリでしか意味を持たない → そのディレクトリ用のルールへ降格

昇格先の判断基準：
- 自分だけに必要なもの → 個人用ルール
- チーム全員に必要なもの → プロジェクト共通ルールへの追加を提案する。提案までとし、勝手に書き換えない。

提案は1回のみ。断られたら繰り返さない。

## 2. 判断の記録

設計上の決定をした直後に、記録を提案する。提案は1回のみ。

```
今の決定を記録に残せます。却下した[代替案]の理由も含めて、ドラフトを書けます。
残しますか。
```

記録を書く場合の規則。

- 却下した選択肢とその理由を必ず含める
- 事実確認が必要な箇所は `[要確認]` と書き、推測で埋めない
- 開発者が確認すべき箇所を明示する
- 記録をチームの共有領域に置く場合、個人用ルールの内容は書き出さない

テンプレート：

```markdown
# ADR-XXXX: [決定の要約]

## ステータス（Status）
[Proposed / Accepted / Superseded by ADR-YYYY]

## 背景（Context）
[この決定が必要になった背景。制約条件。]

## 決定（Decision）
[何を採用したか。]

## 検討した代替案（Alternatives Considered）
- [却下案A]: [却下理由]
- [却下案B]: [却下理由]

## 影響（Consequences）
[この決定によって生じる良い影響と悪い影響。将来の制約。]
```

## 3. 撤退判断

同じ箇所の修正が3回連続で失敗した時点で、修正を続けない。開発者の指示を待たずに停止する。

```
同じ箇所で3回失敗しました。ここで判断を分けます。
(a) 修正を続ける: [残っている手がかりと見込み]
(b) 破棄して分割し直す: [分割案を1行で]
[a または b]を推奨します。理由は[1行]。
```

理解できていないコードへの修正の深追いは、抜け出せない状態に落ちる典型的な経路にあたる。
再生成のコストが低い前提を活かし、早い段階で切る選択肢を必ず提示する。

## 4. ルールの分割

ルールファイルが200行を超えたら、Claudeの側から指摘する。

- 局面ごとにしか使わない内容は、スキル側へ移す
- 特定ディレクトリでしか意味を持たない内容は、そのディレクトリ用のルールへ移す
- 古くなったルールは削除する。矛盾したルールが並ぶと、どちらが選ばれるか不定になる

## 5. 方針との乖離

記録された設計方針と実装の乖離を見つけたら、実装を進める前に指摘する。

```
[ファイル名:行番号]の実装が、[記録名]に記録された方針と異なります。
方針: [記録の内容] / 実装: [実際の内容]
実装を方針に合わせるか、方針を更新するかを決めてください。
```

自分で判断して片方に寄せない。どちらが正かは開発者が決める。

## 6. 定期棚卸し(Check)

個人用CLAUDE.mdの「棚卸し記録」欄にある最終棚卸し日から3〜6ヶ月経過している場合、または利用モデルの世代が変わったタイミングで、Claudeの側から棚卸しを提案する。開発者からの申し出を待たない。

```
最終棚卸しから[経過期間]が経っています。CLAUDE.md・スキル群の棚卸しを提案します。
棚卸しますか。
```

棚卸しで確認する観点。`.claude/CHANGELOG.md`を読み、各ルールが追加された経緯(きっかけ)を踏まえて判断する。

- 矛盾するルール・重複するルールがないか
- 特定モデルの制約を回避するために書かれ、現行モデルでは不要になった制約がないか(例: 旧モデルの弱点を補うための細かい手順指定)
- 参照先(ファイル・スキル名)が変更・削除されて宛先を失ったルールがないか
- CHANGELOG.mdの記載を見ても、そのルールがまだ必要な理由が読み取れないものがないか

該当があれば削除・統合を提案する。提案は1回のみとし、断られたら繰り返さない。
ルールを削除・統合したら、対応するCHANGELOG.mdの履歴もあわせて削除・統合し、肥大化させない。
棚卸しを実施したら、CLAUDE.mdの「棚卸し記録」欄の最終棚卸し日を更新する。

頻度の根拠(参考): 3〜6ヶ月ごとのレビューサイクルおよびモデル世代交代時の監査([CLAUDE.md Decay: The 3–6 Month Review Cadence](https://aiskill.market/blog/claude-md-decay-the-3-6-month-review-cadence))。四半期を目安とする監査サイクルの一般論([Agent Rules Best Practices](https://www.agentrulegen.com/guides/agent-rules-best-practices))。

## 7. 運用上の制約

- 記録が増えるとコンテキスト消費も増える。全件を読み込む運用にはしない。参照は関連するものだけに絞る。
- このスキルに基づく提案は、1セッション中に最大2回まで。
- 断られた提案は繰り返さない。
